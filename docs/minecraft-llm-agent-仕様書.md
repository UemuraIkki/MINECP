# Minecraft自律プレイLLMエージェント 仕様書

- 版: 1.0(構成確定版)
- 日付: 2026-07-23
- 用途: AIエージェントによる実装の入力仕様。本書は構成・責務・インターフェースを定義する。実装詳細(クラス設計・関数分割)は各実装エージェントの裁量とする。

---

## 1. プロジェクト概要

### 1.1 目的

Ollama上で動作するローカルLLM(Qwen系を想定)に、人間の介入なしでMinecraftをプレイさせ、エンダードラゴンの討伐(ゲームクリア)を達成させる。

### 1.2 設計原則

1. **LLMは高レベル意思決定のみ**: tick単位の操作・戦闘・経路探索はLLMに任せない。LLMは「次に何をすべきか」を決め、実行は決定論的なスキル層が担う。
2. **賢さはブリッジに集約**: ゲーム側(Mod)は観測と実行のみ。計画・記憶・プロンプトはすべてブリッジ側。これによりモデル差し替えとプロンプト改善がMod側に影響しない。
3. **単一の真実としてのスキーマ**: Mod・ブリッジ間の通信メッセージはJSON Schemaで一元定義し、双方の実装がこれに従う。

### 1.3 スコープ外

- マルチプレイヤー対応、複数エージェント協調
- Minecraftバージョン追従(1.20.1に固定)
- GUI・可視化ツール(ログで代替。将来課題)

## 2. 技術スタック(確定)

| 項目 | 決定 | 備考 |
|---|---|---|
| Minecraftバージョン | Java Edition 1.20.1(固定) | Fabric/Carpet/Automatoneの情報量と安定性を優先 |
| Modローダー | Fabric | Fabric API使用 |
| エージェント実体 | サーバーサイドModによるFake Player(Carpet方式) | クライアント操作エミュレーションは不採用 |
| 経路探索 | Automatone(Baritoneのライブラリ版フォーク) | Modに組み込み |
| Mod実装言語 | Java(または必要に応じKotlin + Fabric言語アダプタ) | Mixin使用 |
| ブリッジ実装言語 | Python 3.11+ | スキーマ検証にPydantic |
| Mod⇄ブリッジ通信 | WebSocket(双方向) | ブリッジがサーバー、Modがクライアント |
| ブリッジ⇄LLM通信 | Ollama HTTP API(/api/chat) | tool calling(JSON構造化出力)を使用 |
| 推奨モデル | Qwen2.5-14B以上 | 7B級はタスク分解の一貫性が不足 |
| リポジトリ | monorepo | 構成は §9 |

## 3. 全体アーキテクチャ

### 3.1 プロセス構成(3プロセス)

```
[Minecraftサーバー + Fabric Mod] ⇄ WebSocket ⇄ [ブリッジ(Python)] ⇄ HTTP ⇄ [Ollama]
```

| プロセス | 役割 |
|---|---|
| ゲーム側(Mod) | Fake Player生成、観測JSON生成、スキルの決定論的実行、物理的失敗検知 |
| ブリッジ | 計画状態、マイルストーン管理、永続メモリ、反省ループ、プロンプト構築、LLM呼び出し |
| Ollama | LLM推論のみ |

### 3.2 意思決定ループ(イベント駆動 + 定期見直しのハイブリッド)

- **即時判断**: スキル完了・失敗・割り込みイベント(死亡等)の受信時に、ブリッジが次の行動を決定する。
- **定期見直し**: 2分毎に現在の計画全体をLLMに再提示し、計画の妥当性を見直す。
- **非同期原則**: LLM推論中(数秒〜数十秒)もゲーム側は現在のスキル実行を継続する。推論待ちでエージェントを棒立ちにさせない。

## 4. コンポーネント仕様

### 4.1 ゲーム側Mod

責務は以下の3つのみ。**計画・判断ロジックを一切持たない。**

1. **Fake Player管理**: サーバー起動後にFake Playerを1体スポーンさせ、死亡時はリスポーンさせる。リスポーン事実はイベントとしてブリッジに通知する。
2. **観測生成**: §5の観測仕様に従い、状態をJSON化してブリッジにpushする。送信タイミングは (a) スキル完了/失敗時、(b) 定期(5秒毎)、(c) 割り込みイベント発生時。
3. **スキル実行**: ブリッジから受信したスキル命令を決定論的に実行し、結果(成功/失敗+失敗理由)を返す。同時実行は1スキルのみ。実行中に新命令を受けた場合は現行スキルを中断し新命令を優先する。

物理的失敗検知として、座標変化なし60秒でスキルをタイムアウト失敗させる(スタック検知)。

### 4.2 ブリッジ

1. **状態管理**: 最新観測、実行中スキル、マイルストーン進捗、拠点・要塞・死亡地点などの座標記憶を保持する。
2. **永続化**: 上記状態をファイル(JSON)に保存し、プロセス再起動後に復元できること。
3. **プロンプト構築**: システムプロンプト(役割・スキル一覧・マイルストーンDAG)+ 現在状態 + 直近の行動履歴 + 失敗コンテキストからプロンプトを組み立てる。
4. **LLM呼び出しと検証**: tool calling形式でスキル呼び出しを取得する。出力はJSON Schemaで検証し、不正なら再生成させる(最大3回)。3回失敗時はフォールバック行動(安全な既定スキル、例: 拠点へ帰還)を発行する。
5. **反省ループ**: 同一スキルが3回連続失敗した場合、失敗履歴と状況をLLMに提示して代替計画を生成させる(self-reflection)。
6. **ログ**: 全プロンプト、全LLM応答、全スキル命令/結果をタイムスタンプ付きで記録する。

### 4.3 決定論の境界線

| 領域 | 担当 |
|---|---|
| 戦闘全般(対Mob、対ドラゴン) | スクリプト(Mod内ハードコード) |
| ドラゴン戦手順(クリスタル破壊→攻撃) | スクリプト |
| エンドポータル起動の儀式 | スクリプト |
| 経路探索・移動 | Automatone |
| 資源調達の優先順位 | LLM |
| 探索方針(どこを掘るか、どこへ行くか) | LLM |
| 失敗時の代替案 | LLM |

## 5. 観測仕様

観測は要約済みJSONとし、生ブロックデータは送らない(コンテキスト量の抑制)。含める情報:

| 項目 | 内容 |
|---|---|
| 自己状態 | HP、空腹度、座標、向き、ディメンション、ゲーム内時刻 |
| インベントリ | アイテムID + 個数の一覧(空きスロット数含む) |
| 装備 | 手持ち・防具 |
| 周辺要約 | 半径16ブロック内の注目対象のみ: 鉱石、溶岩、水、ポータル、要塞ブロック、チェスト、敵対Mob(種類・距離)、村人 |
| 進捗フラグ | 達成済みマイルストーン、ブレイズロッド数、エンダーパール数、エンダーアイ数 |
| 記憶座標 | 拠点、ネザーポータル、要塞(判明していれば)、直近の死亡地点 |

## 6. スキル仕様

各スキルは「引数 → 決定論的実行 → 結果(成功 / 失敗 + 失敗理由コード)」のインターフェースを持つ。初期セット:

| スキル | 引数 | 概要 |
|---|---|---|
| goto | 座標 or 名前付き地点 | Automatoneで移動 |
| mine | ブロック種、個数 | 対象を探索・採掘(移動含む) |
| craft | アイテムID、個数 | 作業台の確保も内包 |
| smelt | アイテムID、個数 | かまど・燃料の確保も内包 |
| place | ブロックID、相対位置 | 設置 |
| attack | 対象種別 | 戦闘スクリプト起動(逃走判断含む) |
| eat | なし | 食料があれば食べる |
| equip | アイテムID | 装備変更 |
| use_portal | ポータル種別 | ネザー/エンドポータル使用 |
| build_portal | なし | ネザーポータル建設(黒曜石 or バケツ法) |
| throw_ender_eye | なし | 要塞探索。飛行方向を観測として返す |
| fight_dragon | なし | ドラゴン戦フルスクリプト |

失敗理由コードは列挙型として `schema/` で定義する(例: 資材不足、経路不能、対象不発見、死亡、タイムアウト)。理由コードはLLMの再計画の入力になるため、機械可読かつ網羅的であること。

## 7. 通信仕様

### 7.1 メッセージ種別(4種)

| メッセージ | 方向 | 内容 |
|---|---|---|
| observation | Mod → ブリッジ | §5の観測データ |
| skill_command | ブリッジ → Mod | スキル名 + 引数 + 命令ID |
| skill_result | Mod → ブリッジ | 命令ID + 成功/失敗 + 失敗理由コード + 補足 |
| event | Mod → ブリッジ | 割り込み: 死亡、被襲撃、HP危険域、アイテム拾得、実績解除 |

### 7.2 スキーマ管理

- 全メッセージのJSON Schemaを `schema/` ディレクトリで一元管理する。
- Mod・ブリッジ双方の実装エージェントには同一のスキーマ定義を入力として渡す。スキーマ変更は必ず `schema/` を先に更新してから両実装に反映する。
- 全メッセージ共通フィールド: メッセージ種別、タイムスタンプ、シーケンス番号。

### 7.3 接続管理

- ブリッジがWebSocketサーバー、Modがクライアント。
- 切断時、Modは実行中スキルを安全に中断し(その場で停止)、再接続を試行する。再接続後は最新観測を即時送信する。

## 8. 計画・記憶仕様

### 8.1 マイルストーンDAG(プロンプト埋め込み)

クリアまでの中間目標はプロンプトに固定で埋め込む。LLMにゼロから発見させない。

```
木材 → 木ツール → 石ツール → 鉄装備 → 食料安定化
  → ダイヤツール → ネザーポータル → ブレイズロッド×7
  → エンダーパール×12 → エンダーアイ×12 → 要塞発見
  → ポータル起動 → 装備最終確認 → ドラゴン討伐
```

LLMの役割は「現在どのマイルストーンにいて、それを達成するために次にどのスキルを呼ぶか」の判断である。

### 8.2 反省ループ

- 同一スキル3回連続失敗で発動。
- 入力: 失敗履歴(スキル・引数・理由コード)、現在観測、現在計画。
- 出力: 代替計画(スキル列の変更、または前提マイルストーンへの後退)。

### 8.3 死亡リカバリ

- 死亡イベント受信 → リスポーン確認 → 死亡地点を記憶座標に登録 → LLMに「回収に向かうか、装備を作り直すか」を判断させる(アイテム消滅タイマーを考慮した情報を提示する)。

## 9. リポジトリ構成(monorepo)

```
/
├── mod/        Fabric Mod(Java)
├── bridge/     ブリッジ(Python)
├── schema/     JSON Schema(通信メッセージ、失敗理由コード列挙)
├── docs/       本仕様書、プロンプト設計メモ、決定記録(ADR)
└── logs/       実行ログ出力先(git管理外)
```

- `schema/` と `docs/` が単一の真実。実装エージェントへの指示には必ず両方を含める。
- アーキテクチャ上の決定変更はADR(Architecture Decision Record)として `docs/` に追記する。

## 10. 非機能要件

| 項目 | 要件 |
|---|---|
| レイテンシ | LLM意思決定は1〜2分に1回程度を想定。推論待ちでゲーム側を停止させない |
| 出力検証 | LLM出力はスキーマ検証、不正時は最大3回再生成、以後フォールバック行動 |
| スタック検知 | 座標変化なし60秒でスキル失敗(タイムアウト) |
| 永続性 | ブリッジ状態はファイル永続化、再起動で復元 |
| ログ | 全プロンプト/応答/スキル結果を記録。クリア試行1回分を後から完全に追跡できること |
| 再現性 | ワールドシード固定オプションを持つ(デバッグ用)。本番評価はランダムシード |

## 11. 開発フェーズ

| フェーズ | ゴール | 完了条件 |
|---|---|---|
| P1 | 基盤疎通 | Fake Player生成、WebSocket疎通、goto/mineが動作 |
| P2 | 序盤自動化 | 人間介入なしで鉄ツール一式を作成 |
| P3 | ネザー攻略 | ポータル建設、往復、ブレイズロッド7本回収 |
| P4 | 要塞到達 | エンダーアイ作成、要塞発見、ポータル起動 |
| P5 | クリア | ドラゴン討伐スクリプト完遂。ランダムシードでのクリア達成 |

各フェーズ完了時に、ログを用いた失敗分析とプロンプト改善のイテレーションを行う。

---

## 12. 実装エージェントへの指示方針

- Mod実装エージェントとブリッジ実装エージェントは別セッションでよいが、入力に必ず本仕様書 + `schema/` の最新定義を含めること。
- 本仕様書と実装が矛盾する場合は本仕様書を優先し、仕様変更が必要なら先に本仕様書とADRを更新すること。
- スキーマに現れないアドホックなメッセージフィールドの追加を禁止する。
